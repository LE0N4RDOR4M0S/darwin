Como montar credenciais SSH para o serviço `generator`

Este projeto permite que o serviço `generator` faça `git push` para o remoto usando uma chave SSH montada no container.

Passos (no host):

1. Gere uma chave SSH dedicada (recomendado) ou use uma existente:

   powershell

   ```powershell
   ssh-keygen -t rsa -b 4096 -f ./infra/secrets/ssh_id_rsa -N ""
   ```

   Isso criará `./infra/secrets/ssh_id_rsa` (private) e `./infra/secrets/ssh_id_rsa.pub` (public).
2. Adicione a chave pública (`ssh_id_rsa.pub`) ao seu repositório remoto (GitHub/GitLab) como Deploy Key com permissão de write (ou em sua conta como SSH Key se preferir).
3. Ajuste permissões (no Windows, certifique-se de que o arquivo seja lido apenas por você; no Linux/macOS: `chmod 600 infra/secrets/ssh_id_rsa`).
4. O `docker-compose.yml` já monta o arquivo para `/root/.ssh/id_rsa` e define `SSH_KEY_PATH=/root/.ssh/id_rsa` para o container `generator`.
5. Rode o compose:

   powershell

   ```powershell
   docker compose up --build
   ```
6. O `generator` tentará `git push origin <branch>` usando a chave SSH montada. Se preferir não permitir push automático, remova o arquivo `infra/secrets/ssh_id_rsa` ou deixe-o vazio.

Notas de segurança:

- Use uma chave separada para este propósito (não reuse sua chave pessoal principal).
- Se preocupar com segurança em produção, considere usar um segredo gerenciado (Vault, GitHub Actions Secrets, etc.) em vez de montar diretamente o arquivo.

Usando a chave privada no GitHub Actions
----------------------------------------

Para automatizar operações `git push` a partir de um workflow do GitHub Actions (por exemplo, permitir que um job construa e crie branches automaticamente), você pode armazenar a chave privada como um Secret do repositório e no workflow criar o arquivo de chave no runner.

1) No GitHub, vá em Settings > Secrets and variables > Actions > New repository secret.

   - Nome sugerido: `GENERATOR_SSH_KEY`
   - Valor: cole o conteúdo do arquivo `infra/secrets/ssh_id_rsa` (a chave privada inteira).
2) Exemplo de job no workflow (arquivo: `.github/workflows/generator-push.yml`):

```yaml
name: Generator Push

on:
   workflow_dispatch:

jobs:
   push-branch:
      runs-on: ubuntu-latest
      steps:
         - name: Checkout
            uses: actions/checkout@v4

         - name: Setup SSH key
            run: |
               mkdir -p ~/.ssh
               echo "${{ secrets.GENERATOR_SSH_KEY }}" > ~/.ssh/id_rsa
               chmod 600 ~/.ssh/id_rsa
               ssh-keyscan github.com >> ~/.ssh/known_hosts

         - name: Configure git
            run: |
               git config user.name "github-actions[bot]"
               git config user.email "41898282+github-actions[bot]@users.noreply.github.com"

         - name: Create and push branch
            env:
               BRANCH_NAME: "candidate-${{ github.run_id }}"
            run: |
               git checkout -b "$BRANCH_NAME"
               # faça alterações necessárias (por exemplo, aplicar patch)
               git add .
               git commit -m "Auto patch generated by workflow" || echo "no changes to commit"
               git push origin "$BRANCH_NAME"
```

Observações:

- O snippet acima escreve diretamente o secret no arquivo `~/.ssh/id_rsa` no runner e configura permissões estritas.
- `ssh-keyscan` adiciona a chave host de `github.com` para evitar prompts de confirmação.
- Garanta que a chave pública (`ssh_id_rsa.pub`) tenha sido adicionada ao repositório como Deploy Key com permissão de escrita (ou associada à conta/organização adequada).
- Alternativa: usar um token (PAT) como secret e alterar a URL remota para `https://<TOKEN>@github.com/owner/repo.git` antes do push; essa abordagem evita expor chaves privadas, mas exige cuidado para não imprimir o token nos logs.
